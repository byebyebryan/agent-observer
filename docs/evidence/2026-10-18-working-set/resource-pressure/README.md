# Working-set slow-reader pressure qualification

This source-only case exercises the existing `Runtime` encoded-byte budget while slow full-feed readers pin distinct large response bodies. It uses synthetic snapshots and local socketpairs in a fresh process for each installed Python interpreter. It does not start an Observer service or worker, contact a provider, or use Mesh, an SDK, an external client, or a network endpoint.

The worktree pin supplied for this task is `610afaac658903ddd6c466c793f9856b45e9f03e`; its Runtime implementation matches the earlier resource-source pin `bb7b8aab91574fc3a325325ac8debf21b525712a`. Each report records both declared pins and SHA-256 hashes for loaded Observer/test modules, the fixture/schema, and both runner files. The runner does not invoke Git; the module hashes bind the source actually imported by each child. The reports retain only scalar measurements, counts, identity/body digests, and reason codes, never snapshot bodies.

The fixture comes from `tests/test_service_state.provider_snapshot("codex")`, with 2,000 rows, 256-character ASCII titles, and 1,024-character ASCII working directories. The native input is 4,958,818 bytes, below the frozen 8 MiB snapshot limit. Ten rows are active-only and ten are recent-only, for a 20-row expected union; all other rows are parked and outside the 72-hour window. The current activity timestamp and the selected identities stay fixed across all generations. Each accepted snapshot has a new collection ID and advances wall and BOOTTIME samples by 10 seconds. The first title changes by two characters per generation, preserving the allowed title length while making each full DTO body byte-distinct. Both the full seeded input and each complete accepted sample are hashed before processing.

Each process accepts fourteen snapshots with GC disabled. It uses the real `ServiceState.accept`, `Runtime._reserve_working_set`, `_queue`, `_write`, `_room`, `_drop`, and cache pruning paths. `Runtime(collect=False)` starts no worker. The actual stage reservation is 10,502,144 bytes (`MAX_FRAME_BYTES + 2 * MAX_LEDGER_BYTES`); the encoded limit remains 64 MiB and the client cap remains sixteen. The synthetic clock advances with accepted generations, and each peer's `write_started` value comes from the real queue operation.

The socketpair topology starts at the full client cap: thirteen undrained full-feed readers, one drained full-feed reader, one active-feed reader, and one working-set reader. Every slow reader is queued against a distinct generation, then receives one actual partial nonblocking write without the receiver being drained. The three healthy readers fully drain each generation. Their delivered frames are strictly parsed and passed through long-lived stream guards; each full snapshot and active/working-set projection is compared with the direct `ServiceState` frame. Working-set coverage must remain complete with all twenty expected identities. A bounded refusal, missing route, lost healthy peer, or DTO mismatch fails the case.

At every recorded point the report compares `Runtime.encoded_bytes()` with an independent owner/cache/peer charge and verifies that unique live encoded buffers do not exceed the Runtime charge. Peer body parts must be the same objects as their cached body. The inventory records cache revisions, aliases, peer fragments, retained owners, reservation requests, evictions, and drops before and after each relevant operation. This tests the existing encoded-byte accounting; it does not bound Python object graphs, allocator overhead, transient frame graphs, or RSS.

`Runtime._drop` leaves ordinary peer parts intact as it removes and closes a peer. The harness records that behavior and uses only weak references for dropped slow peers; it does not clear their parts during pressure. After `_prune` removes the cache body, `_room`'s local candidate list can still retain the dropped Peer and its body through the remaining synchronous room check. That temporary reference is not included in `Runtime.encoded_bytes()` after cache retirement. Reports record weak-reference reachability immediately after `_room` returns; both dropped Peer objects are gone by then, and neither the Peer nor body survives into the reserve caller. Inclusive transient encoded accounting, physical allocation lifetime and heap/RSS qualification remain open. No cap overrun, production change or physical-memory bound is claimed.

The final paired run is [reports/final6-610afaac/summary.json](reports/final6-610afaac/summary.json). Both pinned interpreters completed all fourteen generations, preserved the exact full/active/working-set row selections, admitted every stage reservation, and had normalized report parity. The comparison omits interpreter identifiers, process RSS, and `bodySha256`: `ServiceState` generates a fresh collection UUID and wall-clock sample for its emitted full snapshot. Within each process, cached route bytes are checked through the actual reader, and the cached full-body digest is checked against that process's direct snapshot. Accepted input digests, selected DTO digests, counter histories, reservation outcomes, drops, cache retirements, and cleanup results match across Python versions.

The 2,000-row full response body is 4,958,833 bytes. At generations 12 and 13, each stage reservation began with current encoded bytes plus the reservation above the 67,108,864-byte limit (70,287,769 and 70,287,774 bytes). Runtime reclaimed enough room by dropping the oldest pinned full readers, `full_slow_00` and then `full_slow_01`; both bodies were 4,958,833 bytes and were still cached/charged when `_drop` ran. Each reservation then fit, with current-plus-stage totals of 65,193,534 and 65,193,539 bytes. The largest measured current encoded charge was 59,786,929 bytes. The active and working-set peers remained connected, the full reader remained available, and all cache/body aliases matched.

Cleanup closes all sixteen receiver sockets, confirms all sender sockets are closed, restores Runtime methods, removes the reservation callback, closes the selector, and clears Runtime peers/caches. The live `ServiceState` intentionally retains 43,813 active-feed bytes and 90,708 working-set bytes; GC-disabled owner-zero is not claimed. Process RSS is included as context only.

Large report JSON files are stored as deterministic gzip files. [storage.json](storage.json) maps each original report name to its compressed file and records both raw and compressed SHA-256 hashes. Original summary hashes refer to the exact decompressed bytes. All 51,498,902 raw bytes were backed up privately and losslessly verified before packaging into 823,061 compressed bytes. The [checkpoint verifier](../review-checkpoint/verify_saved.py) reads them directly; `gzip -dc report.json.gz > report.json` restores the original JSON.

Earlier `reports/final-610afaac`, `reports/final2-610afaac`, and `reports/final3-610afaac` directories preserve harness diagnostics. The first failed before any acceptance because the fixture has no `bootId`; the second exposed misuse of a new stream guard for a later sequence; the third reached pressure but compared the cached full snapshot payload against the sessions array alone. `reports/final4-610afaac` and `reports/final5-610afaac` completed the pressure case and are retained as intermediate runs. Final6 adds normalized cross-interpreter parity, stable alias ordering, and strict parsing/stream-guard validation of the actual healthy full-reader frames. Only final6 is the final paired result. Earlier runner revisions were not retained; their report hashes and diagnostics are preserved, but they cannot be replayed exactly with the final runner.

This qualification is limited to source-level encoded-byte accounting and local socketpair behavior. It does not establish CPU savings, Python heap/RSS bounds, native provider timing, installed service behavior, Mesh/SDK compatibility, delivery over a real transport, or production capacity.
