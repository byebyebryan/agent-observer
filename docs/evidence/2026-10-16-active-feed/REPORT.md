## Behavior and interface

The [supported interface](../../active-feed-interface.md) implements the agreed
[G0 semantics](../../active-feed-proposal.md). Actual-value and complete-census
support remains transient engine metadata. ServiceState caches the fixed Codex
running/user-or-unknown projection once per published generation, before local
IPC. The new native wire, cached source and separate optional Mesh profile carry
selected API 4 bodies, explicit scope coverage and bounded recent-member facts.
No dormant roster, historical receipt bank, arbitrary client predicate or
per-proof native collection is introduced.

The public `PreparedActiveAgentWatch` uses public Mesh snapshot once per
replacement, then current-before-context for every query. Original exact
native support and translated host deadlines independently govern membership,
negative/completeness authority and each body field. Partial omission, expiry
and ledger pruning never retire presentation context. Unknown context after a
missed negative remains an explicit first-pass limitation.

API 4, snapshot/watch 6, full Service 4, write 2 and full Agent profile v3 retain
their meanings and bytes. The three-argument publisher factory still defaults
to the full source. Active publication requires an explicit profile-bound
factory and separately configured source. Core and local service remain
Mesh-free. Python is at least 3.11; core has no required dependencies; optional
Mesh requires `mesh-plus>=0.1.0a23,<0.2` and Mesh requires
`jsonschema>=4.26,<5`. Exact installed declarations and dependencies are in
[interfaces-dependencies.json](interfaces-dependencies.json).

## Controlled cost and remaining adoption

The [producer series](producer-performance.json) has 24 serial installed trials:
per size, ABBA compares a6/full with a7/full, then a6/full with a7/active. Each
trial has six generations and four cached reads per generation, ten selected
rows, and a fixed synthetic roster of 100, 500 or 2,000 total rows. All full-body,
original-lease and whole-membership signatures agree across all eight trials
per size. Candidate projection runs exactly once per generation. Native snapshot,
frame and ledger capacities pass for those fixtures.

| Total rows | Generation CPU a6/full → a7/active, ms each | Cached read CPU a6/full → a7/active, ms each | Measured producer path saving | Full → active bytes/read |
| --- | --- | --- | --- | --- |
| 100 | 29.86 → 41.27 | 17.62 → 5.59 | 36.60% | 169,083 → 44,038 |
| 500 | 149.74 → 200.14 | 89.44 → 5.64 | 56.12% | 833,283 → 44,038 |
| 2,000 | 629.24 → 832.30 | 374.57 → 5.68 | 59.81% | 3,326,033 → 44,038 |

These are medians of the two runs per arm. Cached-read CPU is lower by
68.29%, 93.70% and 98.48%. The added provenance/projection work increases
generation CPU by 30–38%; using the unchanged full feed on the new service
increases this measured full-path workload by 8.76–10.06%. This is a material
cost of the implementation, not a saving for every possible cadence. At 2,000
rows the active comparison adds about 203 ms per generation; the measured
four reads per generation more than recover that cost.

CPU windows cover `ServiceState` acceptance/generation, cached status creation,
encoding and strict parse/selection. Fixture construction, warmup and semantic
hashing are outside them. Encoding is measured per read; this is not a complete
Runtime socket/body-cache benchmark. Native collection, Mesh, transport, RLCD
and memory are outside this series. The entire 145-second series holds the
shared advisory lock; task-owned heavy gates were idle. Load averages were
about 2.0–2.3; unrelated workloads and CPU frequency remain uncontrolled.

Mesh's separately owned [exact-wheel transport series](mesh-peer-performance.json)
uses the same a7/a23 pair, real owned local IPC publisher/Reader/facade, six
generations, three reads per generation and five fixed active rows plus
100/500/2,000 dormant rows. Reported CPU reductions are 82.79%, 96.39% and
99.10%, with equal selected-body signatures and six cached acquisitions per
trial. Active received bytes remain 201,134 per trial. Projection, collection
and service setup are excluded there. Its RSS includes fixture setup; separate
allocation probes cover 100-row full/active and 2,000-row active. Instrumented
2,000-row full allocation exceeded the unchanged harness timeout and is excluded.
These are peer measurements, separate from Observer's independent producer
series; their percentages cannot be added or promoted to whole-application or
live CPU savings. Mesh's [catalog qualification](mesh-peer-catalog.json) is also
peer-owned and outside Observer's acceptance scope.

The [5,000-row capacity probe](capacity-5000.json) rejects input at the unchanged
4,096-row native snapshot/service boundary and creates no new authority.
This is expected bounded rejection, not 5,000-row throughput or native census
acceptance. Native Codex catalog/classification limits remain unchanged;
the 2,000-row controlled fixture does not prove a real 2,000-row native census.
Ledger byte/count overflow and continuity recovery have separate installed tests.

Adoption requires the new service/collector artifact as well as the optional
source/profile/facade and exact Mesh tuple. A reader/publisher upgrade against
the older service cannot supply active-feed1. RLCD must separately configure
the trusted active source/profile factory, retain full-feed rollback, exercise
its uncapped membership/context reconciliation before display limits, and own
service/native, live CPU and device gates. Normal shared launchers, Tmux,
historical writer, provider workflows and service selections are untouched.
